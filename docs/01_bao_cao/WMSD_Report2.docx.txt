I. Project Overview
1. Scope and Purpose
Warehouse Management System Development (WMSD) is a responsive web application for the warehouse operations of Cửa hàng điện nước gạch ốp lát Tân Thương. The project focuses on physical-stock accuracy and traceability for one business establishment with configured warehouse areas and storage locations. The system records and links replenishment requests, purchase orders, supplier confirmations, goods receiving and inspection, lot/location inventory, defective goods, stock movements and transfers, stocktake and approved adjustments, warehouse issues, customer returns, supplier returns, reports and audit history.
Tile inventory is controlled by product, unit of measure, lot, tone, actual calibre, quality status and storage location. Box, piece and square-metre quantities follow the product conversion rule. Stock-affecting transactions preserve their source document, responsible user, time, quantity and status so warehouse staff can trace how recorded inventory changed.
Out of scope for the first release are full accounting, customer debt management, statutory electronic invoicing, and live integration with MISA eShop. MISA eShop remains the store’s existing retail system; WMSD keeps the references required to reconcile warehouse operations without replacing the full retail/accounting solution.
WMSD is developed as the project’s warehouse-focused operational layer and follows the selected Report 1/SRS process baseline 3.1.0, synchronized 25 October 2026: eight BFs, nine features, five application roles, 111 UC IDs (97 active/14 retired), BR-01–33 and 31 screens (28 active/3 retired).
Current fulfilment: verified external order → copied SO → linked WIR/OD → GI-S draft before picking/TO → actual PGI → Warehouse photo POD/DELIVERED → Sales full external receipt PAY-CFM/COMPLETED. No sales pricing, internal invoicing, refund/payment execution or live MISA synchronization.
A1 adds Warehouse failed-delivery intake/GR-FD against undelivered GI-S, without D6, fictitious POD, Owner or customer custody; actual receipt atomically reopens original SO/WIR/OD net demand/version. Claims alone cannot reopen. Preserve gross ledger and transfer replacement OD commitments without duplicate demand; ordinary GR-CR does not reopen.
B1 retains FROZEN immutable snapshot; Warehouse records immediate balance-neutral defect hold, proposes/confirms resolution execution; Owner UC-92/93 approves/posts actual nonzero delta plus RECLASS/location before resolved-scope unlock. Substantiated differences may proceed directly; unclear/chosen recount retains attempt history. Quality-only requires no ADJ=0.
C2 permits Sales to accept/reject own ordinary CR after Warehouse inspection under verified D6 conditions; Owner only eligible exceptions with distinct requester, never overriding D6 exclusions/UNKNOWN. BF-08 has no Owner dispatch/variance/closure approval: Accountant verifies agreement/reconciles/closes UC-83/107, Warehouse posts actual stock events. UC-106 retired; ID/history retained.
Planning impact: assess source-claim concurrency, net reopening/version, typed decisions, B1 closure atomicity and affected UI/API/MongoDB work before estimating revised effort or iteration allocation. Sections 3–4 retain the original 14-week/five-member plan and effort/capacity values, not a new cost or delivery commitment. Current Mermaid and related PNG/HTML exports are updated in the follow-up; only draw.io files remain excluded. Meeting/survey/PDF evidence and external Word/Google Docs are not rewritten/published by this update.

1. Project Process/Methodology
The team applies Agile Scrum as the main software development methodology for WMSD. Scrum is selected because the project is implemented by a small capstone team within a fixed 14-week schedule, while warehouse requirements may still be refined after discussion with the client and supervisor. The methodology allows the team to implement, review, test, and improve the product incrementally instead of waiting until the end of the project to validate the complete warehouse solution.
Scrum is suitable for WMSD for the following reasons:
* The project contains multiple related warehouse modules, including product and unit management, replenishment and purchase orders, goods receiving and inspection, warehouse/location inventory, stock movements and transfers, stocktake and adjustment, stock issue, customer return, supplier return, reporting, and access/audit controls.
*  Several warehouse rules are dependent on actual business practice, such as partial receiving, handling damaged goods, box-piece-m² conversion, lot/tone/actual-calibre tracking, in-transit quantities, and adjustment approval. These rules can be reviewed and refined progressively with feedback.
* The implementation plan already divides the development stage into three iterations: Weeks 6-7, Weeks 8-9, and Weeks 10-11. Each iteration produces a software package and supporting SRS/SDS/testing updates.
*  Frequent review reduces the risk of implementing warehouse flows that appear correct technically but do not match the actual receiving, storage, movement, stocktake, issue, and return processes.
In this project, Scrum responsibilities are applied as follows:
* Supervisor / Mentor: provides project direction, reviews milestone deliverables, gives feedback on scope and major design decisions, and acts similarly to a Product Owner from the academic supervision perspective.
* Project Manager / Scrum Coordinator: maintains the project plan, tracks progress and risks, coordinates iteration planning, facilitates team communication, and ensures that unresolved blockers are handled before they affect milestone delivery.
* Business Analyst: maintains the requirement baseline, use cases, business rules, process flows, and requirement traceability; clarifies warehouse scenarios with the client and converts confirmed business needs into implementable requirements.
* Development Team: implements frontend and backend functions, performs unit testing, integrates modules, fixes defects, and updates technical documentation required for each iteration.
* Tester / QA: reviews testability, prepares and executes integration/system test cases, records defects, verifies fixes, and checks that stock-affecting functions comply with the approved business rules.
  

Figure 2.1 Agile Scrum Process Model
The Scrum process applied by the team is specifically organized as follows:
* Product Backlog: The backlog contains the approved WMSD functions and supporting work items. Items are derived from the SRS and use-case list and are grouped by business capability. The backlog also includes document updates, testing activities, defect fixes, and technical tasks required to complete each software package.
* Backlog Refinement: Before implementation, the team reviews unclear use cases, validation rules, status transitions, actor permissions, and dependencies between modules. For warehouse functions, refinement focuses particularly on how a transaction changes stock quantity, quality status, lot/location information, and source-document traceability.
* Iteration Planning: At the beginning of each implementation iteration, the team selects the functions that can be completed within the two-week capacity. Dependencies are considered so that upstream functions are available before downstream flows are implemented.
* Iteration 1 focuses on establishing the core data and operational foundation required for later warehouse transactions.
* Iteration 2 extends the solution with connected stock movement, transfer, stocktake, issue, or return functions according to the approved iteration scope.
* Iteration 3 completes the remaining functions, resolves integration issues, stabilizes the product, and prepares the software for system testing.
* Iteration Execution: Team members perform detailed design, coding, unit testing, integration, defect correction, and document updates. Tasks are tracked in the agreed project-tracking tool. Functions are not considered complete only because the UI is available; the corresponding business rules and stock-posting behavior must also be verified.
* Daily Coordination: Team members communicate progress, current tasks, blockers, and next actions on working days. Urgent technical or requirement issues are escalated immediately instead of waiting for the weekly meeting.
* Iteration Review: At the end of each iteration, the team demonstrates the completed software package to the supervisor and checks the implemented functions against the agreed SRS and use cases. Feedback that changes scope or behavior is recorded before being added to the next iteration.
* Iteration Retrospective: The team reviews what was completed, delayed, misunderstood, or repeatedly defective. Lessons learned are used to improve task allocation, review discipline, test coverage, and communication in the next iteration.

For WMSD, quality management does not focus only on whether a screen works; it also verifies that inventory quantities, lot/location information, quality status, approvals, and source references remain consistent across connected warehouse transactions.

6. Configuration Management
6.1 Document Management
All project-related documents are centrally stored and collaboratively maintained on Google Drive. This provides one controlled location for reports, project tracking, testing evidence, diagrams, meeting notes and release materials. Google Docs and Google Sheets are used where real-time collaboration is useful, while milestone deliverables are maintained in the required Word/Excel formats.
The document repository is organized into the following main areas:
* Reports - contains Report 1 to Report 7, supporting appendices and milestone submission versions.
* Project Tracking - contains schedule, iteration tracking, work assignments, issue/risk tracking and progress records.
* Requirements & Diagrams - contains approved use-case lists, process diagrams, Draw.io files, PlantUML sources and supporting requirement materials.
* Testing - contains test plans, test cases, test reports, defect logs, evidence and regression results.
* Meeting Notes - contains summaries of supervisor/client discussions, important decisions, action items and unresolved questions.
* Weekly Reports - contains weekly progress reports and records of completed, ongoing and planned work.
* Release Packages - contains milestone software packages and the corresponding approved document set.
Document control rules are applied as follows:
* Version control: Major milestone documents use explicit versions such as v0.9, v1.0, v1.1 and v1.2. A new milestone version is created when the document content changes substantially or is aligned with a new implementation iteration.
* Change log: Significant additions, modifications and deletions are recorded in the Change Log section of the corresponding report.
* Access control: Edit access is limited to the project team and authorized supervising stakeholders; shared review links are used when comments are required.
* Baseline control: Once a report version is used as the baseline for implementation or testing, changes that affect scope or behavior must be reflected in the relevant project tracking record and communicated to the team.
* Backup: Important milestone documents and final submission packages are retained as separate copies so that an earlier approved version can be recovered if necessary.
6.2 Source Code Management
GitHub is used as the central source-code repository and Git is used for version control. The repository is accessible only to authorized project members. The purpose of source-code management is to keep implementation changes traceable, reduce accidental code loss, support parallel development, and control what is integrated into each software package.
The source-code management workflow includes:
* Branch structure: The team maintains a stable main branch and a development/integration branch. New functions and bug fixes are developed on separate feature or fix branches so that unfinished work does not directly affect the stable release.
* Commit convention: Commits use short, meaningful messages describing the change. A commit should represent one logical change where possible so that it can be reviewed or reverted more easily.
* Pull request / merge review: Completed work is merged through a pull request or equivalent review flow. At least one other member reviews important changes before merge, especially changes involving stock quantity, UOM conversion, authorization, or transaction status.
* Developer checks before merge: Relevant unit tests must pass, obvious build/runtime errors must be resolved, and the changed function must match the approved requirement or bug ticket.
* Release control: The stable code corresponding to Software Package Version 1, Version 2 and Version 3 is tagged or otherwise clearly identified in the repository.
* Defect fixes: Bug fixes are linked to the corresponding defect record where possible, and affected integration/system tests are re-executed after the fix.
* Sensitive information: Passwords, secrets, environment credentials and private deployment configuration must not be committed directly to the repository.
